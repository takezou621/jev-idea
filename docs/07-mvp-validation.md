# docs/07 — MVP 有効性検証計画

MVP（判定基盤 + アイデア 1）を実際の開発で使ってみて「サービスとして有効か」を判定する。
評価基準を実装した後の都合で決めると検証にならないため、**この計画を MVP 実装より先に
確定する**（Issue #26）。評価は #29 が、この計画に書かれた事前基準との照合で行う。

## MVP スコープ

| 項目 | 内容 |
|---|---|
| 対象 Issue | #1〜#5（判定基盤: jev-core / メタ分離 / 多数決・observe / ゴールデン・tp/fp / jev-judge MCP）+ #17（アサーション DSL の構造部分）+ #18（PR 判定 (a) の observe 配線）+ #21（Stop フック統合） |

## 検証仮説

Jev 判定が開発ループに介入しても開発を止めず、品質に寄与する。

- **H1（判定品質）**: 実 PR の observe 判定は、人間が見ても正当な指摘を一定以上出す
- **H2（ループ阻害の少なさ）**: 判定の介入は開発のリズムを壊さない速さで返る
- **H3（体感）**: 介入された開発者は「邪魔」と感じない（納得、または役に立つと感じる）
- **H4（価値）**: 少なくとも 1 回、「これがないと困る / 困った」場面が起きる

## 指標と成功基準（確定値）

| 指標 | 定義 | 成功基準 | データ源 |
|---|---|---|---|
| R1 判定品質 | would-block を人間が `tp / fp / unclear` に分類した **tp 率** | 分母 20 件以上で **tp 率 ≥ 60%** | #4 の review コマンド（tp/fp 分類表）+ #18 の observe 記録 |
| R2 ループ阻害の少なさ | judge 全体の所要時間の **p95**。Stop フック完了判定のタイムアウト件数 | **p95 < 2s**、タイムアウト **0 件**（budgetMs 内完結） | 判定ログの所要時間（docs/05 判定ログ仕様）+ #21 のフック動作記録 |
| R3 体感 | 介入ごとの体感タグ（**納得 / 邪魔 / 無関心**）のうち「邪魔」の割合 | 記録 20 件以上で「邪魔」**< 30%** | #28 の体感ログ |
| R4 価値の定性証拠 | 「これがないと困る / 困った」場面の報告数 | **最低 1 件** | #28 の定性メモ |

- FLAKY（境界で block/pass が揺れる同一入力）は docs/05 のルールに従い分母から外す
- unclear は tp 率の計算から除外する（分母からも除く）
- R2 の基準は jev-claude の実測（判定中央値 584ms）に余裕を持たせた初期値。
  p95 を測るのは「最悪の介入がループを止めるか」を見るため

### 介入件数が規定に満たない場合の R3 の扱い

実使用期間終了時点で介入（would-block + Stop フック表示）が 20 件に満たない場合:

- **15〜19 件**: 実使用期間を最長 1 週間延長し、再び判定する
- **14 件以下**: 「邪魔」割合の定量的判定を行わず、体感記録の定性評価へ切り替える。
  R3 は Go/No-Go の判定対象から外し、R1・R2・R4 で判定する

## 実使用期間と手順

- **期間: 2 週間**（docs/01 の「observe で 2 週間」と整合）。#27 の統合完了から起算する
- 手順:
  1. #27 のセットアップ手順に従い、jev-judge 登録・CI observe 配線・Stop フック設定を
     済ませる（所要時間を PR に記録する）
  2. 実使用期間中は通常どおり開発する（検証のための特別な作業はしない）
  3. would-block が出るたび、#4 の review コマンドで tp/fp 分類と体感タグを記録する
  4. 「これがないと困った」場面は、そのつど定性メモに記録する
  5. 週次で #28 の中間サマリコマンドを実行し、件数と内訳を確認する
- 判定ログ・体感ログの実データはリポジトリに入れない（docs/05 の方針 0700 / 0600）。
  docs に載せるのは集計値と匿名化した事例のみ

## Go / 条件付き / No-Go

| 判定 | 条件 | 次のアクション |
|---|---|---|
| **Go** | R1・R2・R3 の成功基準をすべて満たす（R4 は参考情報） | フル実装へ。Phase 1〜4 の残り Issue に AGENTS.md の着手順どおり着手する |
| **条件付き Go** | R2 は満たすが R1 が **40〜59%**。または R1・R2 は満たすが R3 が **30〜50%** | 対象の判定ポイントの質問文・criteria・しきい値を見直す修正 PR を出す → 最低 1 週間の期間を区切って再検証する |
| **No-Go** | R1 < 40%。または再検証後も条件付き Go の基準に届かない | 無効だった部分（どの判定ポイント・どの指標か）を特定して docs に反映。docs/01 の設計見直し（改訂 Issue）を起案する |

- しきい値の途中変更はしない。基準を変えたい場合は #29 で docs/07 の変更として明示してから評価する
- どの判定でも、tp / fp の個別事例は #4 のゴールデン化プロセスに渡す（tp はゴールデン化材料）
- R4 が 0 件でも単独で No-Go にはしない（定性の参考情報として扱う）

## 検証の前提と注意

- MVP の介入は observe のみ（実 block なし）。fp が出ても開発は止まらない。
  止まらないからこそ、R3（邪魔でないか）の体感記録が価値判定の中心になる
- 実使用は人間（利用者本人）が行う。#28 は人間タスクが本体であり、
  エージェントはデータを捏造・埋め合わせしない（AGENTS.md の誠実さのルール）
- 効果の裏付けとして、would-block と実際に人間が指摘した仕様漏れの対応付け
  （docs/01「効果の測定」）を R4 の定性メモに含める
