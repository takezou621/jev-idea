# 2. 思考ログ（思考差分）の同期 — 思考グラフ

Git が「完成したコードの差分」を管理するのに対し、この設計は「**なぜその実装に
至ったか**」の過程 —— 試行錯誤、試して消したアプローチ、検索、エラー対処 —— を
収集し、構造化してコードに紐付ける。後から読む人（人間・AI）が「作者が直面した
詰まりポイント」を即座に同期できる状態を作る。

## 解く問題

「なぜこの不自然な if 文があるのか？」を追うために過去のチャットログやチケットを
探し回る時間は、コードレビューと同程度にリズムを壊す。そして探しても見つからない ——
文脈はエンジニアの記憶と消去されたエディタバッファにしか残っていない。

この設計での Jev の役割は 2 つある:

1. **分類**: 収集した生イベント（コマンド、編集、検索）を「思考ノード」に変換する
   判断。何が試行で何が単なる作業か、何が方針転換で何が反復かは、痕跡の
   パターンマッチで決められない（正規表現で「npm test は検証」と分類した jev-claude
   の痕跡抽出は、コマンドの先頭トークンレベルでしか正しく決められなかった）
2. **裏取り**: 生成モデルに「なぜこの実装か」の説明を書かせるとき、説明が証拠
   イベントと整合するかを検証する。ハルシネーション（存在しない試行の記述）を
   Jev が弾く。生成と判定の分離（overview 原則 5）の典型形

生成モデルに説明を書かせるだけなら既存ツールでできる。この設計の差分は
**説明に証拠を強制する**ことにある。

## アーキテクチャ

```
[Claude Code セッション]                 [非同期パイプライン]
  transcript.jsonl ──────┐
  PreToolUse/PostToolUse ─┤  イベント列     ┌──────────────┐
  (Edit の前後・失敗・検索)─┼──────────────►│ イベント正規化 │ 決定的（jq 的な変換）
  git 操作               ─┘                └──────┬───────┘
                                                 ▼
                                        ┌──────────────┐
                                        │ Jev で分類    │ イベントごと: 調査/変更/検証/方針転換/詰まり
                                        └──────┬───────┘
                                                 ▼
                                        ┌──────────────┐
                                        │ ノード集約    │ 決定的（分類結果を列にしてグループ化）
                                        └──────┬───────┘
                                                 ▼
                                     思考グラフ (.thoughts/graph.jsonl)
                                       ノード: attempt/finding/decision/dead-end
                                       エッジ: supersedes / supports / follows
                                                 │
                              ┌──────────────────┴──────────────────┐
                              ▼                                     ▼
                    git コミットに紐付け                    MCP 参照サーバー
                    (コミット時のフックでマージ)           「この関数の思考履歴」を返す
                                                                        │
                                                                        ▼
                                                    [参照時] 生成モデルが説明文を書く
                                                              └─ Jev が証拠整合を検証
```

設計上の分離は 2 つある:

- **収集は決定的、解釈だけを Jev に**: イベントの正規化・グループ化は機械的に行い、
  Jev に渡すのは分類に必要な最小の文脈のみ。イベント数はセッションで数百になるが、
  1 判定 $0.00007 なので全部分類しても $0.03 以下（overview コスト試算）。**分類を
  集約せず全部投げる**。集約すると「どれを載せたか」の選択自体が新たな誤判定源に
  なる（jev-claude の「状態の切り方」罠）
- **分類は非同期**: パイプラインはセッション終了後（Stop フック + バックグラウンド）
  に走る。レイテンシに寛容で、判定品質を観察しながらしきい値を積める土台

### 収集源（Claude Code 環境を前提）

| 源 | 取れるもの | 思考の証拠としての意味 |
|---|---|---|
| transcript.jsonl | 応答全文、ツール呼び出し、思考 | 意図の直接の記録 |
| PostToolUse フック | Edit の前後 diff | **消したアプローチ**（上書きされた前の内容）が取れる。Git には消したものが残らない |
| Bash の失敗 | エラー出力、終了状態 | 詰まりポイントの一次証拠（jev-claude の failedCommands と同じ抽出） |
| Grep/Glob/WebSearch | 検索クエリ列 | 探していたもの・仮説の跡 |
| git 操作 | stash, checkout, revert, commit | 方針転換の決定的な兆候 |

収集のうち、transcript 読みと Stop フックの配線は jev-claude から再利用する
（transcript.mjs）。PostToolUse（Edit の前後 diff、Bash の終了状態）の収集は
**新規に追加する**。ホスト差分（transcript 形式、フックのペイロード）はアダプタ層に
閉じ込め、解釈（分類）はホスト非依存に保つ（docs/06）。

## データモデル

### イベント（決定的に正規化されたもの）

```jsonc
{
  "id": "ev_01H...",            // 時系列順
  "ts": "2026-09-19T10:30:12Z",
  "kind": "bash|edit|search|git|response",
  "target": "src/verify.ts:42",  // ファイル・行が特定できるものは位置を
  "detail": { /* 種別ごとの最小限の本文。編集は前後 diff、bash はコマンド+終了状態 */ },
  "summary": "命令文から first 200 字"   // evidence に載せる冒頭
}
```

### 思考ノード（Jev の分類を列にして決定的に集約）

```jsonc
{
  "id": "node_...", 
  "kind": "attempt|finding|decision|dead-end|verification",
  "events": ["ev_...", "..."],
  "targets": [
    { "path": "src/verify.ts", "line": 42, "commit": "abc1234", "symbol": "verifyDone" }
  ],
  "label": "分類時に生成した短い事実描述（例: 'xcodegen 試行、スキーマ不一致で失敗'）",
  "supersedes": ["node_..."],   // 別アプローチを試して諦めた、等の関係
  "outcome": "failed|succeeded|abandoned"
}
```

**target の解決**: 行番号はコミットのたびにずれるため、ノードは
(コミットハッシュ, パス, 行, シンボル名) の 4 つ組を持つ（シンボル名は
ts-morph で取得し必須。行だけの参照は取りこぼす）。MCP 参照時はまず HEAD の
シンボル名で一致検索し、見つからなければ `git log --follow` 相当で歴史を遡り、
ノードのコミット時点の状態から解決する。解決できなければ「過去の実装
（コミット X 時点に存在）」の形で提示する（黙って空を返さない）。

ノードの集約規則（決定的）: 同一 target に連続する同種イベントのまとまりを
 1 ノードとし、**失敗→修正→再実行の系列は 1 ノード（outcome: succeeded）に畳む**。
 これは jev-claude の「失敗の引継ぎ」罠（成功後も失敗が残り誤ブロックした実運用
 事例）と同じ失敗形を避けるための決まりである。

### ストレージ

- `<repo>/.thoughts/`（判定ログと同じ機密扱い）にローカル保存。**git 管理は
  オプトイン**（デフォルト無効）。transcript には秘密を含むコマンド出力が混入
  しうるため、共有前にシークレットスキャン（決定的パターン + Jev 判定 1 回）を
  必須にする
- コミットへの紐付け: pre-commit フックが「このコミットが触る行に対応する
  ノードの要約」をコミットメッセージのトレーラー形式で添える（
  `Thought-Ref: node_id...`）。本体はローカルに置いたまま参照可能にする

## Jev 判定仕様

### 判定ポイント (A): イベント分類（非同期、イベントごと）

| 項目 | 設計 |
|---|---|
| 質問 1a / 1b / 1c（3 criteria） | このイベント列（前後 5 イベントの文脈付き）は、(a) コードを変更する試みか、(b) 情報を得る調査か、(c) 動作を確かめる検証か。3 値分類は 1 質問に混ぜず 3 criteria に分ける |
| 質問 2 | 直前のノード（同 target の直近の分類結果）と同じ意図の反復か、方針を変えた新しい試みか |
| 質問 3 | このイベント列は詰まり（失敗や困惑の兆候: エラーの反復、試行の放棄、範囲の広い検索）を含むか |
| evidence | 対象イベント + 前後 5 イベントの summary、直近ノードの label。**応答全文は渡さない**（判定語混入の防止と、質問が同じ evidence で独立に答えられるよう最小限に切る） |
| 確定規則（質問 1a-1c） | 最大の p が 0.5 未満 → `unclear`。上位 2 値の p の差が 0.2 未満 → `unclear`。それ以外は最大 p の分類 |
| わからない | `unclear` ノードとして残す（捨てない）。捨てると後の裏取りの証拠が欠ける |
| failMode | open（分類できないイベントは生のまま残す） |

質問 2 は 2 段判定: 質問 1 が確定してから意味を持つ。質問 1 が unclear の
イベントに質問 2 を聞かない（overview 原則 3）。質問 3 は質問 1 と独立なため
同時に聞いてよい。

分類 → ノード kind の対応（集約時に決定的に適用する）:

| 質問 1 の確定 | 質問 2（前ノードありのとき） | ノード kind |
|---|---|---|
| 変更 | — | `attempt` |
| 検証 | — | `verification` |
| 調査 | — | `finding` |
| — | 方針転換 | 前ノードが `attempt` なら前ノードを `dead-end` に変更し、新ノードを `attempt` として `supersedes` を張る |

outcome（`succeeded` / `failed` / `abandoned`）は Jev でなく**機械的事実**で決める:
系列の最後の検証コマンドの終了状態とコミットの有無。最終検証が成功 → `succeeded`、
失敗のまま系列が終了 → `dead-end`。判定不能のままの系列は `abandoned` とする。

### 判定ポイント (B): 生成説明の裏取り（同期、参照時）

MCP で「この関数の思考履歴」を返すとき、生成モデルの説明文と証拠の整合を検証する。

| 項目 | 設計 |
|---|---|
| 質問 1 | この説明文の各主張は、提示したノード（イベント）の記録と整合しているか |
| 質問 2 | 説明文は、記録に存在しない試行・理由に言及していないか（ハルシネーション） |
| evidence | 説明文、対応するノード一覧（label + 代表イベントの summary） |
| しきい値 | 質問 2（ハルシネーション）は **3 回判定の多数決**（docs/05 の多数決 helper）で true が多数のとき**説明の全体提示を止め**、証拠ノード一覧のみを出す。ばらつき大（docs/05 の規則で unknown）も止める側に倒す（誤った文脈を植えるより証拠だけの方が害が小さい）。質問 1 は p ≥ 0.75 で該当主張への「記録なし」注記 |
| わからない | 証拠一覧のみ表示（説明文には出さない） |
| failMode | open（裏取り不能なら証拠一覧のみ） |

質問 2 を block 級のしきい値にする理由: 存在しない試行の記述は、見た人に
誤った文脈を植える点で最も害が大きく、jev-claude の「主張と痕跡の突き合わせ」
（完了判定の核）と同じ形状の判定である。

### 判定ポイント (C): 共有前の機密確認

git 共有をオプトインするとき 1 回。

| 項目 | 設計 |
|---|---|
| 質問 1 | このノード集合の中に、認証情報・個人を特定できる情報・公開してよいか曖昧な社内情報は含まれていないか |
| evidence | 共有対象ノードの summary 全文 |
| しきい値 | p > 0.4 で共有を止め、該当ノード一覧を人間へ（**安全側に倒す**。取り返しがつかないのは共有後）。unknown も止める側 |
| failMode | **closed**（判定不能なら共有しない）。フローを止めるのではなく、共有という不可逆操作の前だけ止める |

## 参照インターフェース（MCP）

`thought-graph` MCP サーバーが 2 つのツールを出す:

- `thoughts_for(path|symbol)`: そのファイル・シンボルに紐づくノードを時系列で返す
  （dead-end を先に。詰まりポイントは後続の attempt と supersedes で繋がっている）
- `explain_with_evidence(path|symbol, question)`: 証拠ノード一覧 + 生成説明 +
  裏取り結果（判定ポイント B）。「なぜこの if 文があるか」の問いに、
  **証拠が付いた説明**で答える

AI エージェントがこの MCP を使うと、過去セッションの文脈を脳内同期してから
作業を始められる。これが「AI への効能」の本体である。MCP クライアントであれば
Claude Code 以外（goose 等）からも同じサーバーを登録して使える（docs/06）。

## 実装計画

| フェーズ | 内容 | 完了条件 |
|---|---|---|
| 2-1 | 収集: フック配線 + イベント正規化。**Jev を使わない**。決定的な部分を先に固める | 実セッションでイベント列が欠落なく取れる |
| 2-2 | 判定 A（分類）+ ノード集約。observe モード | 分類結果を人間が 20 件以上レビューし、分類ラベルの妥当性を確定 |
| 2-3 | ストレージ + コミット紐付け（pre-commit フック） | コミットメッセージに Thought-Ref が付き、`git log` からノードへ辿れる |
| 2-4 | MCP 参照サーバー + 判定 B（裏取り） | 「なぜこの実装か」への回答が証拠付きで出る。ハルシネーション事例を 3 件以上捕捉 |
| 2-5 | 判定 C（機密）+ 共有オプトイン | シークレットを埋めたダミーセッションで共有が止まる |

## リスクと罠

| 罠 | この設計での出現形 | 対処 |
|---|---|---|
| 痕跡の正規表現分類 | 「試行錯誤」を正規表現で決めると jev-claude の「grep xcodegen がビルド痕跡になる」問題と同型の誤分類が起きる | 分類は Jev。決定的な規則は unclear 時のフォールバック専用 |
| 状態の切り方 | transcript 全文を渡すと長く、判定が弱まる（jev-claude: 件数で切ると肝心の痕跡が落ちた実測） | summary + 前後 5 イベントの固定窓。応答全文は渡さない |
| ヒアドキュメント | Edit で書き込まれた内容が「編集」と誤分類される類の問題 | 種別ごとに本文の切り方を決定論化し、Jev には種別を信じさせる（種別の判断と内容の解釈を混ぜない） |
| 分類語への反応 | ノード label（前回の分類結果）を evidence に載せると、label の語に引きずられる | label は前後関係の文脈としてのみ渡し、質問文に判定語を使わない。label 生成自体も Jev なら「事実描述のみ」を質問に含める |
| ターン境界 | transcript のメタレコードをプロンプトと誤認（jev-claude 実測） | 収集段階（決定的）でレコード種別を確定させ、分類にメタを渡さない |
| 秘密の混入 | `.thoughts/` をうっかり push | デフォルト git 管理外 + .gitignore + 判定 C が closed |
| グラフの膨張 | 長期運用でノードが増え参照が弱まる | ノードの TTL と「参照頻度 0 かつ対象コードが消えた」ノードのアーカイブ（決定的）。クエリ時の関連性フィルタは将来課題 |

## 検証方法

- **分類の正解データ**: 実セッション 3 本（jev-claude の golden 抽出と同じ流れ）から
  イベントを起こし、人間が正解ラベルを付けて回帰にする。expected は人手で確定
- **敵対スイート**: 同一コマンドの反復（反復か方針転換かの境界）、成功裏に終わる
  詰まり（最初に失敗して直しただけ）、説明文への偽装（「試したが諦めた」と書いた
  が記録にない）、シークレットを含む summary
- **効果の測定**: 「なぜこの実装か」への回答にかかった時間の比較（思考グラフあり/
  なし）。ハルシネーション捕捉数の記録
- **正直な限界**: 収集は Claude Code に限定される（エディタ上の人間の試行錯誤は
  別の収集経路が要り、本設計の範囲外）。ノード集約の規則は運用で変わる可能性が
  高く、集約を変えると過去の分類と整合しなくなる —— そのためゴールデンは
  イベント単位で持ち、集約結果は持ち直す
