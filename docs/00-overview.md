# 全体設計 — Jev を判定エンジンにする 4 つのアイデア

この設計書群は、4 つのアイデアを **Jev（TypeSafe AI の判定専用モデル）を判定エンジンと
して**実現するためのもの。各アイデアの詳細は個別の設計書にあり、この文書は共通の
前提・アーキテクチャ・設計原則・ロードマップを扱う。

- [01-requirement-assertions.md](01-requirement-assertions.md) — 要件アサーション駆動開発
- [02-thought-graph.md](02-thought-graph.md) — 思考ログ（思考差分）の同期
- [03-instant-fork.md](03-instant-fork.md) — 実行状態ごと複製するインスタント・フォーク
- [04-dual-generation.md](04-dual-generation.md) — プロダクションコードとテストコードの双対自動生成
- [05-jev-core.md](05-jev-core.md) — 共通判定レイヤー（judge() インターフェース、確率の確定規則、メタ分離プロトコル）

## Jev の特性（設計の前提）

実測値は姉妹リポジトリ jev-claude で確定済み。設計はこの数字に合わせて引く。

| 項目 | 値 | 設計への意味 |
|---|---|---|
| レイテンシ | 中央値 584ms/回 | 同期的に挟める（ユーザー入力の直後など）が、ループで 10 回以上回すなら非同期が望ましい |
| コスト | $0.000067 未満/回（入力 ~1,600 トークン） | 「毎回」呼んでよい。集約して呼ぶ最適化は不要な水準 |
| 回答の形 | criteria（質問群）ごとに**確率 + confidence** | 二値でなく確率で返る。二値化する場所がすべて誤判定の入り口になる |
| 出力 | 判定のみ（長文生成はしない） | 生成は大きなモデル、検証は Jev、という分担が基本形 |
| 入力単価 | $0.042 / 1M トークン | 状態テキストを 5〜10KB 載せても無視できるコスト。載せる量はレイテンシで決める |

コストで最適化する必要がないぶん、設計の争点は常に同じところへ集約される:

1. **Jev に何を聞くか**（質問の切り方）
2. **状態テキストに何を載せるか**（証拠の切り方）
3. **確率をどう潰すか**（しきい値と「わからない」の扱い）
4. **Jev が不通のとき何が起きるか**（フェイルオープン / フェイルクローズの選択）

## 共通の問題意識

4 つのアイデアが刺すのは「コードを書く手のリズムを止める原因」である。

| リズムを止める原因 | 対応するアイデア | 変換後の形 |
|---|---|---|
| 仕様漏れを指摘するレビュー往復 | 1: 要件アサーション | 仕様違反 → コンパイルエラー + 判定 |
| 文脈を探す時間（なぜこの実装か） | 2: 思考グラフ | 「作者が直面した詰まり」の即時同期 |
| 再現手順・環境構築 | 3: インスタント・フォーク | バグの瞬間への直接アタッチ |
| 実装・テストの重複記述 | 4: 双対自動生成 | 制約定義とエッジケースの審判に専念 |

共通する発想は、これらを**人の判断から「機械が繰り返せる判定」に変換する**こと。
ただしすべてを機械に委ねるのではない。変換できない判断（要件の妥当性の最終決定、
境界ケースの審判、収束の承認）は明示的に人間へ残す。設計書の各所にある
「人間へのエスカレーション」は手抜きではなく仕様である。

## 共通アーキテクチャ

各アイデアを独立したツールとして設計しつつ、判定まわりは 1 つの共通レイヤー
（`packages/core`、仮称 jev-core）に集約する。jev-claude の `jev-lib.mjs` の一般化。

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  1: 要件     │  │  2: 思考     │  │  3: フォーク │  │  4: 双対     │
│  アサーション │  │  グラフ      │  │             │  │  生成        │
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘
       │ 判定ポイント定義（質問・状態テキスト・しきい値・フェイル挙動）
       ▼                ▼                ▼                ▼
┌─────────────────────────────────────────────────────────────────┐
│ jev-core（共通判定レイヤー）                                       │
│  - judge(criteria[], evidence): 確率回答 → 正規化 → 二値化         │
│  - 質問スキーマの検証 / confidence ガード / 中間帯の扱い            │
│  - フェイルオープン（総予算タイムアウト・AbortSignal）              │
│  - 判定ログ（answers/reasons/トークン数、0700/0600）               │
│  - ゴールデン回帰 / 敵対スイート / observe モード                  │
└────────────────────────────┬────────────────────────────────────┘
                             ▼
                 Jev API（api.typesafe.ai/v1/systemone）
```

各アイデアが jev-core に持たせるのは「判定ポイントの定義」だけである:

| 定義項目 | 内容 |
|---|---|
| `id` | 判定ポイントの識別子（ログとゴールデンで使う） |
| `criteria` | Jev に投げる質問群。**1 質問 1 判断**に切り分ける |
| `evidence()` | 状態テキストの組立て。判定語（「違反」「正常」等）を含めない |
| `decision()` | 回答の二値化からアクションへの写像。どの確率でどのアクションを取るか |
| `failMode` | Jev 不通時の挙動（`open` = 通す / `closed` = 止める / `escalate` = 人間へ） |
| `gate` | 操作の可逆性（`reversible` / `irreversible`）。observe の適用可否と closed の許可範囲を決める |

型定義・確率の確定規則・メタ分離プロトコルの詳細は
[05-jev-core.md](05-jev-core.md) に書く。

## 共通設計原則

jev-claude で本番 5 回の誤ブロックから確定した原則。4 つのアイデアすべてに適用する。

### 1. 判定器の故障でフローを止めない（フェイルオープンを基本とする）

キー無し・ネットワーク断・タイムアウト・API 仕様変更のすべてで判定は `unknown` を返し、
呼び出し側は「未判定」として扱う。例外は明示的に選択した場合のみ（アイデア 1 の
法的アサーションでマージゲートにする場合など）。SDK のタイムアウトは 1 試行あたり
しか管理しないので、総予算は `AbortSignal` で自前で持つ（jev-claude と同じ）。

### 2. 確率を二値に潰す場所を最小化し、「わからない」を人間へ

Jev の回答は確率である。潰し方の罠は実測済み:

- `score` は `[0, criteria.length - 1]` の尺度。正規化してから比較する。
- `confidence` の低い回答は「わからない」として扱う。欠落は「確信なし」に倒す。
- `isTrue === false` を「偽」として使わない。p=0.47 は「偽」でなく「わからない」。
  「偽」は `isFalse`（確率が十分低い）のときだけ。

「わからない」の行き先は各判定ポイントで定義する。既定は人間へのエスカレーション
（レビュー通知、PR コメント、確認プロンプト）または安全側のアクション。
しきい値付近（既定 0.6）は境界で block/pass が振れる**実測**があるため、
境界が重要な判定はしきい値で決めずに人間へ出す。

### 3. 1 質問 1 判断。質問を混ぜない

「検証が必要か」と「検証が欠けているか」を 1 質問にすると、前者が不明のときに
後者が確定した扱いになり誤判定する（実運用で発生）。すべての判定ポイントは
質問を独立に切り、依存する質問は**前段の回答が確定したときだけ**後段に渡す
（2 段判定）。1 回の呼び出しに複数の criteria を載せるのは、質問同士が
独立しているときだけにする。

### 4. 状態テキストに判定語を混ぜない

Jev は状態テキストに含まれる語そのものに反応する（transcript に表示した block 理由
「TODO/スタブ」への反応で誤ブロック 2 回、実測）。evidence の組立てでは:

- 判定対象の中身（diff、コード、思考ログ、メモリ内容）を**生のまま**載せる
- 呼び出し側が先に付けた「違反しています」「OK」等の語を載せない
- 機械的な検証痕跡（コマンド、終了状態、出力末尾）を優先し、散文的な説明を
  減らす

生成モデルの出力（アイデア 4 のコード・テスト、アイデア 2 の説明文）には
「この実装は仕様に整合します」のような自己主張文が混入しうる。これは
**インジェクション**として扱い、jev-core は evidence の中の指示文を
構造的に分離する（対象データとメタの区別をプロトコルで持つ）。

### 5. 生成と判定を分離する

Jev は生成しない。長文を生む必要がある場面（コード生成、テスト生成、説明文生成、
思考ノードの要約）は大きな生成モデルの担当であり、Jev はその**検証**に回る。
この分担は 4 アイデアすべてで同じ。判定 1 回あたりのコストが生成の 1/100 以下
であることと、作業者本人の自己評価は甘いことが、この分担の根拠である。

### 6. 回帰はゴールデンで積む。expected は人間が確定する

各判定ポイントにゴールデン（入力 → 期待判定）を持ち、しきい値やプロンプトを
変えるたびに回す。実運用の判定は後から人間が tp / fp / unclear に分類し
（jev-claude の `review.mjs` の流れを jev-core に一般化）、tp を拾って
ゴールデンに足す。expected を機械で決めない —— 分類の人手が効果実証の数字になる。

### 7. しきい値を変える前に observe する

`observe` モード（判定するが block しない、`would-block` を記録）を jev-core に
組み込み、block 型の判定ポイント（`gate: "reversible"`）はすべて対応する。
新しい block 型の判定ポイントは observe で運用データを積んでから block を
有効にする。

**例外**: `failMode: closed` のゲート（不可逆操作の前の判定。docs/02 判定 C の
共有前機密、docs/03 判定 (a) の fork 前機密）は observe を適用しない。
block しない observe を不可逆操作の前で走らせることは「ゲートを外した本番運用」
そのものであるため。closed ゲートの導入検証は合成ゴールデンとステージング環境で
行う。詳細は [05-jev-core.md](05-jev-core.md) を参照。

### 8. 秘密の扱いは設計に組み込む

evidence にはコマンド出力・diff・思考ログ・メモリ内容が載る。jev-claude と同じ
機密扱い（ディレクトリ 0700 / ファイル 0600、ログは判定結果と内訳のみ、
block したときだけスナップショット）を jev-core に持たせる。アイデア 3 では
メモリ内容そのものが対象になるため、機密検出自体が判定ポイントになる。

## 4 アイデアの Jev の関わり方の違い

| | Jev が判定するもの | Jev が要る理由 | 判定の数 |
|---|---|---|---|
| 1: 要件アサーション | 宣言と実装の整合。要件定義自体の妥当性 | コンパイラは型の互換しか見ない。アサーションの**意味**（法律・業務ルール）と実装のずれは自然言語の判断が必要 | PR あたり 1〜5 回 |
| 2: 思考グラフ | イベントの分類（調査/変更/検証、方針転換、詰まり）。生成説明文の裏取り | 「試行錯誤か単なる作業か」は痕跡のパターンで決められない。説明文のハルシネーション検証にも使う | イベントあたり 1 回（非同期） |
| 3: インスタント・フォーク | スナップショットの機密の有無。復元の再現性 | メモリ・状態内の機密の判定は正規表現で完全にはできない。再現判定は症状の突き合わせ | スナップショットあたり 2〜3 回 |
| 4: 双対自動生成 | 反例は仕様違反か。テストの強度。収束判定 | GAN 構造の審判。審判が甘いと提案者と反証者の軋みが発散する。判定の中立性が本質 | ループあたり 5〜10 回 |

アイデア 4 が最も Jev が本質（判定がループの中心）、アイデア 3 が最も周辺
（本体はスナップショット技術で、Jev は安全性のゲート）。この位置づけの差が
ロードマップの順序になる。

## コスト試算（概算）

判定 1 回 $0.000067、584ms。全アイデアで Jev のコストは無視できる水準であり、
律速はレイテンシの直列回数と生成モデルのターン数である。

| | 1 単位あたりの判定数 | 直列レイテンシ | コスト/単位 |
|---|---|---|---|
| 1: PR 1 本 | 1〜5 | 同期 1 回（CI 内なので許容） | $0.0003 以下 |
| 2: セッション 1 本 | 数百（非同期） | バックグラウンド | $0.03 以下 |
| 3: スナップショット 1 件 | 2〜3 | 取得前に同期 1 回 | $0.0002 以下 |
| 4: 収束 1 回 | 5〜10 | ループは非同期（人間は待たない） | $0.0007 以下 |

## ロードマップ

実装の着手順。判定が本質でインフラ要らずのものから、OS レベルの検証が要るものへ。

1. **Phase 0: jev-core の抽出** — jev-lib.mjs を一般化。質問スキーマ、確率の正規化、
   observe、判定ログ、ゴールデン回帰、tp/fp 分類。ここが最初。全アイデアの足場。
2. **Phase 1: アイデア 4（双対自動生成）** — 追加インフラ不要（CLI + Claude Code の
   スキル/エージェントで完結）。判定がループの中心であり、jev-core の質が直接
   出力の質になる。ジェネレータ（提案者・反証者）と審判の分離をここで固める。
3. **Phase 2: アイデア 2（思考グラフ）** — Claude Code フックの資産（収集配線）を
   jev-claude から直接再利用。イベント分類は非同期なのでレイテンシに寛容で、
   判定品質を積み上げる土台に向く。MCP で参照口を出す。
4. **Phase 3: アイデア 1（要件アサーション）** — 型レベル DSL と検証器生成の設計が
   先に要る（コンパイラ/言語ワークの比重が高い）。Jev は「宣言と実装の整合」の
   補完判定として後から乗る。CI 統合から入り、インライン判定へ。
5. **Phase 4: アイデア 3（インスタント・フォーク）** — CRIU / Firecracker の検証が
   要るため最後。Phase 1〜3 の間に L0（リクエスト記録・リプレイ）だけ先行実装
   できる。機密検出の判定は単独でも価値がある。

各フェーズの完了条件は個別設計書の「実装計画」、および Phase 0 の本体である
[05-jev-core.md](05-jev-core.md) に書く。
