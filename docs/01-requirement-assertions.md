# 1. 要件アサーション駆動開発

ビジネスロジックの要件そのものを型シグネチャに組み込み、構造で保証できる部分は
コンパイル時に、**意味**でしか保証できない部分は Jev の判定で検証する。

## 解く問題

従来の型はデータの構造（`int`, `string`, `User`）しか保証しない。年齢範囲や
法規制のような要件は、実装の奥・テスト・レビュアーの記憶に散らばる。エンジニアが
最も時間を取られるのはコードを書く時間ではなく、「この実装で例外ケースが発生しないか
考える時間」と「PR レビューで仕様漏れを指摘される往復」である。

この設計の狙いは 2 層に分けること:

- **構造で証明できる部分**（範囲、形式、必須性）は型レベル DSL + ランタイム検証器で
  コンパイル・実行時に弾く
- **意味でしか保証できない部分**（`CheckedBy<LegalCheck>` の `LegalCheck` が何を
  意味し、実装がそれと整合するか）は宣言（アサーション定義）と実装を突き合わせて
  **判定**する。ここが Jev の仕事

Jev が要る理由: コンパイラは型の互換しか見ない。`age: Number & WithinRange<18, 99>
& CheckedBy<LegalCheck>` と宣言しても、そのフィールドを検証せずに使うコードは
型として合法であり、コンパイルは通る。宣言の**意味**と実装の整合は自然言語の判断
であり、レビュアーの脳内でしか行われていなかったものを判定ポイントに変換する。

## アーキテクチャ

```
要件（法律・仕様書・口頭指示）
        │ 人間がアサーション定義として書く
        ▼
┌──────────────────────────────────────────────┐
│ アサーション定義 (.req.ts / requirements/)      │
│  WithinRange<18,99> ──► 構造検証器（決定的）    │
│  CheckedBy<LegalCheck> ──► 意味の宣言（Jev 対象）│
└──────┬───────────────────────────┬───────────┘
       ▼                           ▼
  コンパイル/実行時           判定レイヤー（jev-core）
  （型エラー・検証器が弾く）   (a) PR 判定: 実装 diff と触れるアサーション
                              (b) 定義判定: アサーション定義と根拠文書
                              (c) 網羅判定: 境界テストの有無
```

### 層 1: アサーション DSL（構造部分、Jev を使わない）

TypeScript の型エイリアスで宣言し、アサーション定義からランタイム検証器を
生成する（コード生成またはデコレータ実行）。

```ts
// requirements/user.req.ts
export const AdultAge = require.number("adult-age", {
  within: [18, 99],
  severity: "legal",
  basis: "規約第 3 条: 本サービスは 18 歳以上 99 歳以下を対象とする",
  basisRef: { type: "doc", path: "docs/terms.md", section: "3" },
});

export type User = {
  age: TypeOf<typeof AdultAge> & CheckedBy<"LegalCheck">;
};
```

`WithinRange` 相当は検証器（実行時に境界値で弾く）と型（ブランド型）のペアに
コンパイルされる。この層のルール: **検証器が書けない制約は型に書かない**。
書けないものは `CheckedBy<>` として宣言だけ行い、層 2 に逃がす。これは
jev-claude の「検証の要否」罠と同型の分離であり、「構造で証明できるか」を
 DSL が強制する。

### 層 2: 意味の判定（Jev）

3 つの判定ポイント。すべて PR と Claude Code セッションに配線する。

#### (a) PR 判定 — 宣言と実装の整合

PR の diff から、その diff が**触れる**アサーションを特定し（ファイル・シンボルの
依存グラフで機械的に特定、判定ではない）、実装と突き合わせる。

- 特定の仕組み: アサーション定義のシンボル → 使用箇所を ts-morph で逆引きし、
  使用箇所を含む関数・クラスへの diff の到達を依存グラフで見る
- 判定に渡す evidence: アサーション定義全文（basis 含む）、diff、
  関連する検証器の実行痕跡（CI のテスト出力）
- Jev 落ちた場合: `failMode: open`（警告コメントのみ）。ただしアサーションに
  `severity: "legal"` が付いている場合は `failMode: closed` を選べる
  （未判定ならマージ不可）。**既定は open**。closed にするなら運用として
  Jev の到達性（API 止めで全部のマージが止まる）をチームで承認した上で

#### (b) 定義判定 — 要件自体の妥当性

アサーション定義の変更（basis の文言、範囲の変更）を PR にしたとき、根拠文書
（法律の条文、仕様書の節）と突き合わせる。要件の最終判断は人間だが、
**根拠文書と定義の齟齬**は判定できる（「定義の 18〜99 は根拠条文の文言と
整合するか」）。

- evidence: アサーション定義の diff、`basis` が指す根拠文書の該当節
- ここで人間に残すもの: 根拠文書自体が古い/誤っている場合。Jev は「整合しない」
  としか言えず、「どちらが正しいか」は判断しない

#### (c) 網羅判定 — 境界テストの有無

`WithinRange<18, 99>` が付く値型について、境界値（18, 99, 17, 100）のテストが
PR 内または既存テストに存在するかを機械的に確認し（テストコードから定数の
抽出、決定的）、**足りない境界が要件上重要か**を判定する。CI で毎回走る。

### Claude Code への配線

CI に加えて、開発中の即時フィードバックとして Stop フック（jev-claude の完成判定
と組み合わせる）に「このターンで触れたアサーションがあるか」を足す。触れている
のに PR 判定を通す前の段階では、block 理由に「アサーション `adult-age` に触れた
変更がある」と載せる（判定語ではなく事実のみ）。

実装（#21）: Stop フックから `jev-stop` CLI（`jev-judge` MCP サーバー経由。CI の
`jev-observe` と同一の実行口）を呼ぶ。設計からの確定事項:

- 「このターンで触れた」は `git diff HEAD`（未コミットの tracked 変更）の**近似**。
  ターン単位の正確な抽出は transcript 収集（docs/02・#22）の範囲。untracked
  （新規ファイル）は対象外
- observe 中の**判定結果**（escalate・status: failed を含む）では停止を妨げない
  （exit 0）。検出事実は `{"systemMessage": ...}` でユーザーに表示する（Stop フックの
  exit 0 + 素の stdout は表示されないため）。`decision: "block"` で停止を妨げる実
  block は #19 以降。配線エラー（git 不在など判定が走らなかった場合）は jev-observe
  と同じ分け方で非ブロックの exit 1（stderr 表示。判定の結果と混ぜない）
- 配線はリポジトリ同梱の `.claude/settings.json`。タイムアウト時は Claude Code が
  フック出力を破棄し判定なしで停止が続行される（fail-open 方向）
- 判定ポイント・しきい値・evidence 組立て・2 段判定の制御は CI と同一（定義は
  1 か所 — docs/06）。差分は diff の範囲（refspec）だけ

## Jev 判定仕様

### 判定ポイント (a): 宣言と実装の整合

| 項目 | 設計 |
|---|---|
| 質問 1 | この diff は、フィールドに付されたアサーションの制約を実行時に**迂回していないか**（検証前の値の使用、制約の無効化、検証器のスキップ） |
| 質問 2 | 変更後の実装は、アサーションの basis が表す業務上の制約と整合しているか |
| 質問 3 | アサーションに違反しうる入力経路が diff 内に追加されていないか（直に構築されるオブジェクト、キャスト、`as any`） |
| evidence | アサーション定義（basis 含む）、diff、検証器実行痕跡、`as`/`any`/直構築の機械検出結果 |
| しきい値 | 質問 1 は回答層の `true` 判定（既定: p ≥ 0.75 かつ confidence ≥ 0.5、docs/05）で block。質問 2・3 は true しきい値を 0.6 に上書きした上で warn（block ではない） |
| わからない | コメントとして人間へ（「アサーション adult-age の整合を確認してください」+ evidence 要約） |
| failMode | open（severity: legal は closed を選択可能） |
| observe | 導入時は observe で 2 週間。実 PR での fp 率を見てから block を有効化 |

質問 1 と 2 を混ぜない理由: 迂回の検出は「機械的に見える事実」で足りるが、
basis との整合は意味の判断で、確信度の特性が違う。実測でも、質問間の不整合
（「検証の要否が不明」なのに「検証の欠如」を根拠に判定した）による誤ブロックが
 jev-claude で 1 件発生し、質問の分離・2 段判定で解消済みである。

### 判定ポイント (b): 要件定義の妥当性

| 項目 | 設計 |
|---|---|
| 質問 1 | このアサーション定義（範囲・条件）は、根拠文書の該当箇所の文言と整合しているか |
| 質問 2 | 根拠文書の該当箇所は、このフィールドの意味に対応しているか（根拠の取り違えの検出） |
| evidence | 定義の diff、根拠文書の該当節（`basis` が URL/パス/引用で指す） |
| しきい値 | いずれも 0.6 で「要確認」ラベル。block はしない（要件は最終的に人間が承認） |
| わからない | 常に人間の PR 承認に乗せる（この判定ポイントは補助） |
| failMode | open |

### 判定ポイント (c): 境界の網羅

質問は 1 つのみ。

| 項目 | 設計 |
|---|---|
| 質問 1 | このフィールドの要件上の境界（basis から読み取れるもの）と既存テストの境界値を比べたとき、**要件上重要**な境界のうち未検証のものはあるか |
| evidence | アサーション定義、既存テストの境界値リスト（機械抽出） |
| しきい値 | 0.6 で CI の警告。block しない |
| failMode | open |

機械抽出の規則: テストコードから境界値を**リテラルでしか**抽出しない。計算・
間接参照（`MIN_AGE + 1`、fixture 参照等）で書かれた境界は「抽出不能」として
数え、未検証扱いにしない。抽出不能は別枠「人間確認推奨」として表示する
（誤検出が Jev への誤った evidence になるのを防ぐ）。

## データモデル

```jsonc
// requirements/ に置くアサーション定義の実体（DSL から生成・管理される）
{
  "id": "adult-age",
  "kind": "within-range",          // 構造検証可能な種類
  "within": [18, 99],
  "basis": "規約第 3 条: 本サービスは 18 歳以上 99 歳以下を対象とする",
  "basisRef": { "type": "doc", "path": "docs/terms.md", "section": "3" },
  "severity": "legal",             // legal | business | style
  "checkedBy": ["LegalCheck"]      // 意味の宣言（Jev 判定の対象）
}

// 意味の宣言
{
  "id": "LegalCheck",
  "question": "このコードは成人年齢の法的要件を正しく扱っているか",
  "basisRef": { "type": "url", "path": "https://laws.e-gov.go.jp/..." },
  "requiresHumanApproval": true
}
```

`basis` を必須にするのがこの設計の要である。根拠のないアサーションは
意味の判定（(b)）が成立せず、Jev に渡す evidence が「宣言だけ」になる。
DSL は basis 無しの定義をコンパイルエラーにする。

`basisRef` の `type: "url"` の扱い: 判定 (b) は CI 内で走るため、**CI が外部 URL
を fetch して本文を取ることはしない**（ネットワーク依存・本文の変化が判定の
再現性を壊す）。`url` は出典の参照先を示すだけに使い、判定に渡す本文は必ず
取得時点の固定引用 `quote` を一緒に持たせる（`{ type: "url", path: "...",
quote: "第 3 条 …" }`）。quote 無しの url 参照は DSL がエラーにする。
外部の本文が変わったことの検知は対象外（将来課題）。

## 実装計画

| フェーズ | 内容 | 完了条件 |
|---|---|---|
| 3-1 | DSL の構造部分: 型エイリアス + 検証器生成 + basis 必須チェック | サンプル型がコンパイルされ、検証器が境界値で弾く |
| 3-2 | PR 判定 (a) の配線: GitHub Actions + jev-core。observe モードで運用 | 実 PR で observe 判定を積み、fp 率を人間分類で測る |
| 3-3 | block 有効化しきい値の確定、ゴールデン化 | tp/fp の記録が 20 件以上、境界が flaky リストに入れられている |
| 3-4 | 判定 (b)(c)、severity: legal の closed オプション | (b)(c) が PR コメントとして動く |
| 3-5 | Claude Code Stop フック統合 | 触れたアサーションが block 理由に事実として載る |

## リスクと罠（jev-claude の実測からの適用）

| 罠 | この設計での出現形 | 対処 |
|---|---|---|
| 理由文字列への反応 | PR コメントや commit message に「アサーション違反」と書いてあると、diff に違反がなくても反応する | evidence から呼び出し側の評価語を除去。機械検出結果は「`as` 使用 3 箇所」のような事実の形で渡す |
| 中間帯の断定 | 「整合するかわからない」を「違反」として block | isFalse ガード。質問 2 は block ではなく警告 |
| 質問の混在 | 「迂回していないか」が不明のときに「整合していない」が確定した扱いになる | 質問 1 と 2 の分離。1 が不明なら 2 に進まない（2 段判定）。順序制御は判定ではなく配線（呼び出し側）が action ベースで行う。停止条件: 質問 1 の escalate / block / status: failed（block は #19 以降。observe 中は would-block が pass 変換されるため現れない） |
| コンパイラへの過信 | 「型が通ったから要件は満たされた」という誤解を DSL 利用者が持つ | ドキュメントとエラーメッセージで「CheckedBy は宣言であり検証は別」を明示。LSP ホバーにも出す |
| 別リポジトリ問題（未解決課題の同型） | マルチパッケージでアサーション定義と使用箇所が別リポジトリだと依存グラフが途切れる | Phase 3-1 ではモノレポのみ対応と明記。別リポジトリ対応は将来課題として残す |
| ReDoS 的な定義 | アサーション定義に正規表現を置けるようにしたとき、悪意ある/壊れたパターンで判定前に落ちる | jev-claude と同じ上限（サイズ・件数・パターン長・入れ子量指定子の検査）を DSL パーサに置く |

## 検証方法

- **合成ゴールデン**: 整合する実装/迂回する実装/曖昧な実装の 3 種 × アサーション
  3 種 = 9 ケースから始め、実 PR から実ケースを `extract` 相当で追加
- **敵対スイート**: `as any` での迂回、検証器の条件反転、basis と矛盾する範囲の
  定義、根拠の取り違え（別条文への誤リンク）、判定語混入 evidence
- **効果の測定**: PR レビューでの仕様漏れ指摘回数の前後比較（observe 中の
  would-block と、実際に人間が指摘した仕様漏れの対応付け）
- **正直な限界**: 「整合」判定はレビュアーの代替にはならない。アーキテクチャ上の
  逸脱（層の飛び越し等）はこの仕組みの守備範囲外。宣言と実装が**別 PR で
  別々に**変わった場合の取り残しもあり、定義変更時の使用箇所一覧の強制表示で
  緩和する
