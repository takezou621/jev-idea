# 3. インスタント・フォーク — 実行状態ごと複製・共有する

本番・STG でバグが発生した瞬間の実行状態（メモリ、環境変数、外部依存の応答、
データベースの関連行）をスナップショットとして保存し、ローカル/クラウド開発環境へ
復元して、**再現手順を踏まずに**バグの瞬間へアタッチする。

4 アイデアの中で Jev が最も周辺にある。本体はスナップショット技術（記録・転送・
復元）であり、Jev は安全性のゲート（機密の有無）と品質の保証（復元の再現性）を
担う。そのぶん本体の技術選定が設計の中心になる。

## 解く問題

バグ修正の前段は「再現」である: ローカルで DB をシードし、認証を通し、特定の画面を
操作して状態を作る。この間、コードは 1 行も書けない。さらに「手元で再現しない」
という往復が発生する。修正したいのはコードであり、再現手順の確立ではない。

「メモリごと複製」は最も強力だが最も制約が多い。この設計は**レイヤー分け**で
段階的に到達する: 論理状態（リクエスト・DB）から始め、プロセスメモリ、VM 全体へ。

## アーキテクチャ

### スナップショットの 3 レイヤー

| レイヤー | 内容 | 技術 | 制約 | 再現の忠実度 |
|---|---|---|---|---|
| L0 論理状態 | HTTP リクエスト/レスポンス、DB の関連行、セッション、キューメッセージ | リクエスト記録（透過プロキシ/SDK フック）+ DB サブセット抽出 | ミドルウェアの挿入が要る。非決定性（時間・乱数）は変換で固定 | 低（入力が同じで内部状態は違う） |
| L1 プロセス | プロセスツリーのメモリ、fd、環境変数 | CRIU（Linux） | 同一 OS/アーキテクチャ。状態の詰まった長時間プロセス向け | 高 |
| L2 VM | ゲストメモリ・デバイス状態全体 | Firecracker / QEMU スナップショット | スナップショット元が VM 内で動いている必要。ストレージ I/O のリストア | 最高 |

L0 → L1 → L2 の順で実装する。L0 は既存技術の組合せで Phase 4 の先行実装が可能
であり、L1/L2 は検証（CRIU のランタイム互換、Firecracker のストレージ差分リストア）
を要するため最後に置く。

### データフロー

```
[本番/STG]                          [スナップショットストア]           [開発環境]
  snapper 常駐エージェント              オブジェクトストレージ           jev fork <id>
  ┌────────────────────┐   暗号化    ┌──────────────────┐   復元   ┌──────────────────┐
  │ トリガ: エラー/手動  ├─────────►│ スナップショット   ├────────►│ devcontainer で   │
  │ 状態の収集(レイヤー別)│  (KMS)   │ + メタデータ      │          │ プロセス復元/     │
  │ Jev 機密判定 (a)     │          │ + 機密マーカー     │          │ リプレイ開始      │
  └────────────────────┘          └──────────────────┘          └───────┬──────────┘
                                                                        ▼
                                                                Jev 再現判定 (b):
                                                                元の症状と復元後の
                                                                観測を突き合わせ
```

### コンポーネント

| コンポーネント | 役割 |
|---|---|
| `snapper` | 本番/STG に常駐。トリガ（未処理例外、特定のログ、手動 `jev snapshot`）で状態を収集。収集はレイヤーごとに独立したドライバ（L0: HTTP 記録+DB サブセット、L1: CRIU ラッパ、L2: Firecracker API） |
| スナップショットストア | オブジェクトストレージ（暗号化必須）。メタデータ（OS/アーキ/依存のバージョン、元の症状、機密マーカー）を一緒に持つ |
| `jev fork <id>` | 開発側 CLI。環境の互換性を機械的に検査し、devcontainer またはクラウド環境へ復元。復元後にリプレイ/プロセス再開 |
| `jev attach` | 復元済み状態へのデバッガ（DAP）接続。バグの瞬間からデバッグが始まる |

### 決定的な部分と判定の部分の分離

- 機械検査（決定的）: OS・アーキテクチャ・言語ランタイム・主要依存のバージョン
  突き合わせ。ここで弾けるものは Jev に聞かない
- 判定（Jev）: バージョン表では見えない「復元の妥当性」と「機密」。正規表現で
  メモリ内の全機密を完全には拾えない（アイデア 2 と同様、パターンマッチの
  守備範囲を超える判断）

## Jev 判定仕様

### 判定ポイント (a): スナップショット取得前の機密判定

メモリ・環境変数・リクエスト内容にはトークン・PII・個人情報が溜まる。
**共有・保存前に**判定する。保存そのもの（本人環境のみ）は暗号化で済むが、
他人環境への fork は不可逆な公開であり、ここを閉じる。

| 項目 | 設計 |
|---|---|
| 質問 1 | このスナップショット（環境変数一覧、リクエストヘッダ、メモリ内の文字列候補の抽出結果）には、認証情報・PII・社外秘と推定される値が含まれているか |
| 質問 2 | 含まれる場合、リダクション（マスキング）で復元の有用性を保ったまま除去できる値か（URL 中のトークン等は除去でき、署名済みペイロードは除去すると壊れる） |
| evidence | 機密パターンの機械検出結果（決定的スキャンの事実列）、環境変数キー一覧、リクエストのサマリ。**メモリ全文は渡さない**（入力サイズと秘密の二次送出を防ぐ） |
| しきい値 | 質問 1 は p > 0.4 で「fork 時にリダクション必須」マーカーを付け、質問 2 で可否を分ける。共有先が他人の場合はリダクション不可なら fork を止める |
| わからない | 機密あり扱い（**安全側**）。リダクション後に人間の承認へ |
| failMode | **closed**（fork の前だけ）。取得・本人利用は止めない |

判定は保存時 1 回、fork 時（共有スコープが広がる瞬間）に 1 回。保存時の結果を
fork 時に再利用せず再判定する（スナップショットへの依存が変わるため）。

### 判定ポイント (b): 復元後の再現判定

`jev fork` 完了時に、元の症状が復元環境で起きているかを突き合わせる。
「再現しない」というやり取りを、fork の直後に潰すのが目的。

| 項目 | 設計 |
|---|---|
| 質問 1 | 元の症状（エラーメッセージ、スタックトレース、異常な応答）は、復元後の観測（起動直後のログ、同条件での 1 リクエストの応答）に現れているか |
| 質問 2 | 復元環境の観測には、元の環境と本質的に異なる点（バージョン差、設定差、データ差）が現れていないか |
| evidence | 元の症状（snapper が記録）、復元後の観測（決定的に収集したログと応答の末尾）、バージョン表の機械比較結果（差分のみ） |
| しきい値 | 質問 1 は **3 回判定の多数決**（docs/05 の多数決 helper）で true が多数のとき「再現確認済み」、それ以外（多数でない・ばらつき大・unknown）は「再現未確認」を明示してユーザーに伝える。block ではない（デバッグは続行できる）。表示分岐が flaky な単発判定に依存しないよう多数決にする |
| わからない | 「再現は確認できず、観測はこれ」と証拠だけ出す |
| failMode | open |

### L0 限定: リプレイの非決定性の判定

L0 ではプロセスメモリを復元できないため、挙動の再現はリクエストリプレイに依存する。
時間・乱数・外部 API の非決定性は、対象ごとに次の手段で**機械的に**固定する:

| 非決定性 | 固定手段 |
|---|---|
| 時刻 | ランタイム起動時に clock モックを注入（Node なら `--require` / `--import` で凍結時刻の Date / timer 層へ差し替え）。OS レベル（libfaketime）はランタイム互換の制約が大きいため第 2 候補 |
| 乱数 | 起動引数でシードを注入し、記録時のシードをメタデータに保存 |
| 外部 API | 透過プロキシが記録済み応答を返却（一致条件: メソッド + URL + ボディハッシュ） |

固定できた保証はない（ランタイムが OS 時刻を直接読む、ネイティブ乱数等がある）。
**固定漏れによる非決定性**は以下の判定で補う。

| 項目 | 設計 |
|---|---|
| 質問 1 | 同一リクエストの 2 回のリプレイ応答に、処理の意味に影響する差（状態の分岐が変わるほどの差）はあるか |
| evidence | 2 回の応答の構造化 diff（機械生成） |
| しきい値 | p > 0.5 で「非決定性あり: リプレイ結果の信頼度が下がる」を表示 |
| failMode | open |

## メタデータ（スナップショットのスキーマ）

```jsonc
{
  "id": "snap_...",
  "layer": "L0",                      // L0 | L1 | L2
  "trigger": { "type": "unhandled-error", "log": "TypeError: ... (末尾 2KB)" },
  "environment": {
    "os": "ubuntu-22.04", "arch": "arm64",
    "runtime": "node-22.3", "deps": { /* ロックファイルのハッシュ */ }
  },
  "secrets": { "scannedAt": "...", "verdict": "redaction-required", "markers": ["env:STRIPE_KEY"] },
  "reproduction": { "symptom": "...", "verifiedAt": null },
  "blob": "s3://.../snap_....enc"     // 暗号化実体。KMS キーは別管理
}
```

`trigger.log` はアイデア 2 の「詰まりポイント」と構造を共有する（思考グラフの
dead-end ノードからスナップショットへの参照を張れる）。

## 実装計画

| フェーズ | 内容 | 完了条件 |
|---|---|---|
| 4-0 | L0 の先行実装: HTTP リクエスト記録（透過プロキシ）+ DB サブセット抽出 + ローカルリプレイ。**時刻・乱数の固定手段の技術検証を含む** | サンプルアプリでバグ発生→記録→ローカルリプレイが動き、同一シードの 2 回リプレイ応答が一致する |
| 4-1 | snapper 常駐化 + トリガ + ストア（暗号化、メタデータ） | エラーをフックしたスナップショットが 1 コマンドで取れる |
| 4-2 | 判定 (a)（機密）の実装。closed モード。**導入検証は合成ゴールデンとステージングのみ**（observe は使えない — docs/05） | メモリにトークンを積んだダミープロセスで fork が止まる |
| 4-3 | `jev fork` + 判定 (b)（再現判定、多数決） | 復元→判定→「再現確認済み」表示が動く |
| 4-4 | L1 の検証: CRIU の devcontainer 復元（同一 OS/アーキに限定） | Node サーバのプロセスメモリ復元が動く |
| 4-5 | L2 の検証: Firecracker スナップショット + 差分リストア。**Firecracker は KVM 前提で macOS 開発機では直接動かない**。検証は CI 上の Linux ランナーまたはクラウド環境で行う | VM 内のバグ状態を Firecracker で再開できる |

4-4/4-5 は研究要素が強い。L0/L1 のみで価値が出る構成（L0: ほとんどの Web バグ、
L1: 状態を持つ長時間プロセス）であり、L2 は失敗しても範囲を切れる。

## リスクと罠

| 罠 | この設計での出現形 | 対処 |
|---|---|---|
| 機密の二次送出 | 機密判定のためにメモリ内容を Jev に送ること自体が機密の送出になる | メモリ全文は送らない。決定的スキャンの**事実列**（「env に STRIPE_KEY あり」等、値を除く）だけを evidence にする |
| 正規表現機密検出への過信 | 「スキャンを通ったから安全」という誤解 | 機械スキャンは「事実の列」を作るのみで、判定は Jev + 人間承認。スキャン通過を安全の根拠にしない |
| 再現判定の過信 | 「再現確認済み」の表示が復元環境の正しさの証明と誤解される | 表示は「症状の一致を観測した」まで。判定は補助であり、デバッグ自体は続行できる |
| バージョン差の無視 | 機械検査で同一バージョンでもパッチ差で挙動が変わる | バージョン表は厳密一致を要求し、差があれば fork 前に止める（決定的）。判定ポイント (b) 質問 2 が表で見えない差を拾う |
| スナップショットの鮮度 | 時間が経ったスナップショットは依存が古くなり復元が壊れる | メタデータの鮮度を fork 時に機械検査し、古いものは警告（決定的） |
| ストアの権限 | スナップショットは本番の状態の複製であり、DB のダンプ以上に機密 | ストアは暗号化 + KMS、アクセスは取得者のみを既定に。共有は判定 (a) の closed ゲートを必ず通る |
| CRIU の互換性崩壊 | ランタイムのバージョンアップで CRIU 復元が壊れる（実績の多い問題） | L1 は「同一 OS/アーキ/ランタイム」に限定し、検証スイート（4-4 の復元テスト）を CI で常時回す |

## 検証方法

- **機密判定**: 機密（API キー、PII、JWT）を意図的に積んだプロセスのスナップショット
  20 パターンで止まること、逆に機密なしで止まらないこと（fp ゼロ確認）。expected は
  人手で確定しゴールデン化
- **再現判定**: 意図的に壊したサンプルアプリで「再現する/しない」両方のケースを
  作り、判定が裏取れることを回帰にする
- **敵対スイート**: 環境変数キーだけ見せた曖昧ケース（値なしでは判断不能）、
  値が Base64 で符号化された機密、構造化 diff が空だが意味差のあるリプレイ
- **効果の測定**: 「再現手順の確立 + 再現の確認」にかかった時間の前後比較。
  fork の成功率（判定 (b) が「再現確認済み」を出せた割合）
- **正直な限界**: L0 は内部状態を復元しないので、メモリ破壊や競合状態のバグは
  範囲外（L1/L2 の領域）。本番メモリのダンプは法規制上の制約（PII の域外持ち出し
  等）があり、運用ポリシーの合意が前提。この設計は技術的な可否のみを扱う
